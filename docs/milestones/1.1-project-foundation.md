# Milestone 1.1 — Project foundation

**Status:** Complete

**Completed:** 2026-07-01

**Pull request:** [#4 Implement project foundation](https://github.com/vijendharv/USCollegeSelection/pull/4)

## Objective

Create a clean, tested Python foundation for later college-selection work. Establish configuration, logging, networking, and storage boundaries without prematurely implementing DuckDB schemas, student-domain models, document parsing, or ChatGPT integration.

## Delivered

### Python project and dependencies

- Created a Python 3.12+ package named `us-college-selection`.
- Added `pyproject.toml` for runtime dependencies and development tooling.
- Added `uv.lock` so development and CI can install reproducible dependency versions.
- Added `.python-version` to state the expected local Python version.
- Added `.gitignore` coverage for virtual environments, secrets, downloaded datasets, DuckDB files, uploads, sessions, reports, and frontend artifacts.

Runtime dependencies are intentionally small:

- Pydantic and Pydantic Settings for typed configuration.
- HTTPX for the networking layer.

Development dependencies include pytest, Ruff, mypy, and coverage.

### Configuration

`app/config.py` provides one typed `Settings` object with safe local defaults. Settings can be overridden through `USCS_`-prefixed environment variables.

The initial settings cover:

- environment name;
- log level;
- public-data directory;
- private session directory;
- outbound request timeout; and
- maximum download size.

The settings object validates ranges and creates the local directories owned by the foundation.

### Structured logging

`app/logging_config.py` configures standard Python logging to emit one JSON object per line. Records contain a UTC timestamp, severity, logger, message, and exception details when present.

This uses the standard library rather than adding a logging platform or framework.

### Health command

The application can be exercised locally with:

```bash
uv run python -m app health
```

The command loads configuration, configures logging, creates configured directories, and returns a JSON health document. A successful response resembles:

```json
{
  "data_dir": "data",
  "environment": "development",
  "service": "us-college-selection",
  "session_dir": "sessions",
  "status": "ok"
}
```

### Networking boundary

`app/networking` is the only package permitted to import HTTPX. It defines a small `NetworkClient` protocol and a concrete synchronous `HttpClient`.

The client provides:

- text and JSON requests;
- streamed file downloads;
- HTTP/HTTPS URL validation;
- request timeouts and redirects;
- a consistent user-agent;
- configured response-size limits;
- cleanup of partial downloads; and
- retrieval metadata including final URL, status, timestamp, and ETag.

HTTP failures are translated into the application-level `NetworkError` so later services do not depend on HTTPX exception types.

### Storage boundary

`app/storage` defines separate contracts for:

- `CollegeStore`, which will be implemented with DuckDB in Milestone 1.3; and
- `SessionFileStore`, which owns private temporary uploads and reports.

`LocalSessionFileStore` is implemented. It creates random session directories, restricts all paths to one configured root, rejects path-traversal IDs, and deletes complete sessions.

Student files are therefore kept out of the future public college database.

### Test doubles and boundary enforcement

The test suite includes small fake networking and college-storage implementations. Later service tests can use them without making web requests or opening a real database.

An import-boundary test scans application source and enforces:

- HTTPX imports remain inside `app/networking`.
- DuckDB imports remain inside `app/storage`.

## Design decisions

- Use one Python package rather than splitting the MVP into services.
- Keep networking synchronous until measured requirements justify asynchronous code.
- Define DuckDB behind `CollegeStore`, but defer its schema and implementation to Milestone 1.3.
- Implement local session storage now because upload/report path safety is foundational.
- Use standard-library JSON logging instead of a logging dependency or hosted service.
- Use protocols and small fakes instead of a dependency-injection framework.
- Enforce architectural boundaries with a simple test rather than a separate architecture tool.

## How to use it

Install all locked runtime and development dependencies:

```bash
uv sync --all-groups
```

Run the test suite:

```bash
uv run pytest
```

Run static checks:

```bash
uv run ruff check .
uv run ruff format --check .
uv run mypy app tests
```

Run the health command:

```bash
uv run python -m app health
```
