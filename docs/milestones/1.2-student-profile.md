# Milestone 1.2 — Student profile and manual academics

**Status:** Complete

**Completed:** 2026-07-01

**Pull request:** [#6 Implement student profile models](https://github.com/vijendharv/USCollegeSelection/pull/6)

## Objective

Create one strict, canonical student-profile representation for manual entry and future transcript extraction. Allow users to save partial information while identifying exactly what is missing or ambiguous before college analysis begins.

## Delivered

### Strict domain-model foundation

Added a shared `DomainModel` base using Pydantic. Domain models:

- reject unknown input fields;
- strip surrounding string whitespace;
- validate assignments after creation; and
- serialize consistently for tools, storage, reports, and tests.

The models contain no database, HTTP, UI, or classification logic.

### Courses and grades

`Course` represents one repeatable manual or transcript-derived course row. It supports:

- stable generated course IDs;
- subject and optional course name;
- school year and academic term;
- regular, Honors, AP, IB, dual-enrollment, other, and unknown levels;
- the school's original course-level label;
- exact original grade plus optional numeric interpretation;
- attempted and earned credits;
- completed, in-progress, repeated, withdrawn, pass/fail, and unknown statuses; and
- manual, transcript, or app-calculated provenance where applicable.

Partial rows are permitted. Missing grades and unknown course levels become assessment findings rather than invented values. Impossible credit combinations are rejected.

### GPA variants

`GPARecord` stores each reported or calculated GPA independently with:

- value and scale;
- weighted, unweighted, or unknown type;
- cumulative, yearly, term, core, or other scope;
- manual, transcript, or app-calculated source;
- optional school year and term; and
- a required conversion-rule version for app-calculated GPAs.

The model never combines weighted and unweighted values and never overwrites a reported GPA with an app-calculated one.

### Standardized tests

`TestScore` supports SAT, ACT, AP, and IB totals or sections. Test-specific validation rejects scores outside their published numeric scales while preserving optional section and test-date information.

### Student preferences

`StudentPreferences` supports:

- state of residence;
- intended entry year and term;
- multiple intended majors;
- optional annual budget and its meaning;
- preferred and excluded states;
- schools already being considered; and
- test-submission plans.

State codes are normalized, duplicate text entries are removed without changing their first spelling, and contradictory geography preferences are rejected. Budget remains optional, but a supplied amount must state whether it means net price, out-of-pocket cost, or published cost.

### Canonical profile

`StudentProfile` combines:

- a schema version;
- a stable profile ID;
- the partial academic record; and
- student preferences.

The profile can be created empty and built incrementally. This supports a manual-entry workflow without forcing users to invent data merely to save progress.

### Completeness assessment

`assess_profile` evaluates a profile without modifying it. It returns:

- `ready_for_analysis`;
- stable warning codes;
- human-readable messages;
- precise profile paths; and
- info, warning, or blocking severity.

Blocking findings currently cover missing academic evidence, residence state, entry year, entry term, and intended major. Non-blocking findings cover missing course grades, unknown course levels, unknown GPA types, absent course-level history, and class rank without class size.

Readiness requires no blocking findings. Optional budget and test scores never block analysis.

## Design decisions

- Allow empty and partial profiles so manual entry can be saved incrementally.
- Keep structural impossibilities as validation errors and ordinary missing information as assessment warnings.
- Preserve every GPA variant as a separate record instead of calculating one preferred GPA.
- Require provenance and versioning for app-calculated GPA values.
- Keep course rigor explicit; unknown does not silently become regular or advanced.
- Use stable warning codes and paths so a future UI can focus the relevant field.
- Keep readiness assessment deterministic and independent of admissions classification.
- Avoid introducing a student database or persistence format before storage requirements are known.

## How to use it

```python
from app.models import (
    AcademicRecord,
    Course,
    CourseLevel,
    EntryTerm,
    Grade,
    StudentPreferences,
    StudentProfile,
    assess_profile,
)

profile = StudentProfile(
    academic=AcademicRecord(
        courses=[
            Course(
                subject="Mathematics",
                name="AP Calculus AB",
                level=CourseLevel.AP,
                grade=Grade(original="A"),
            )
        ]
    ),
    preferences=StudentPreferences(
        residence_state="CA",
        intended_entry_year=2027,
        intended_entry_term=EntryTerm.FALL,
        intended_majors=["Computer Science"],
    ),
)

assessment = assess_profile(profile)
assert assessment.ready_for_analysis
```

Models can be serialized without inventing optional values:

```python
payload = profile.model_dump(mode="json", exclude_none=True)
```
